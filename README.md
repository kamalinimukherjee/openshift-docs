# Layered Products Docs

The main branch contains the sync server files.

## sync.yaml

If you are not working on the sync server itself but on a layered product, the only fine you want to modify is `sync.yaml`.

Most parameters in it should be self-explanatory. You have a project, you set the distro name for it, and define one or several branches. For the sync to work, a branch of the configured name must already exist in both the OpenShift docs GutHub repository (the source) and this GitLab repository (the target).

The "settings" parameters might require some explanation. They are necessary because the automatic conversion for Portal (which is actually the `build_for_portal` script in GitHub, this server just runs it) cannot add the subtitle and description in `docinfo.xml` files. So while every other file in the GitLab branch is simply overwritten by the autogenerated content, something has to be done to keep your work on `docinfo.xml`.

So fot every project you can set the `keepfiles` setting to one of two options:

- `gitlab`: this is what the old sync server did so it is now the default. You edit the `docinfo.xml` files in this GitLab repo and they are preserved by the sync server while it overwrites/deletes all other files.

- `github`: with this setting, you must add `docinfo.xml` files to every directory in your GitHub repository that corresponds to a Portal book (these are normally the first-level directories such as `about`, each of these directories is in a `Dir` parameter in `_topic_map.yml`).The sync server automatically copies these files alongside the AsciiDoc content. With this setting you do not need to do anything in your product's GitLab branch at all!

The global `keepnames` setting lets you add other files that are treated in the same way as `docinfo.xml`, in case the need arises. Do not remove `docinfo.xml` from the setting.

## Sync server files

If you want to work on the sync server, here is a brief overview of the files and directories.

- `.gitlab-ci.yml` defines the CI jobs including the sync server itself and triggering a rebuild of the custom image for it (by pushing to a github repo).

- `setup-repos.sh` clones both the GitHub and GitLab repos. It takes the access token as a parameter, used when running in CI. Without a parameter it assumes it is running locally, so if you have an SSH key with write access to the GitLab repo, things will work too.

- `yaml-to-sh.py` is a script that reads `sync.yaml` and writes `sync.sh` and also `keepnames`, the list of filenames to keep (so `docinfo.xml`). After running this script, the CI runs the `sync.sh` file itself, and that file, in turn, runs `run-sync.sh` setting up the right environment variables for every branch to process.

- `run-sync.sh` is where the main processing happens. It has comments describing every step.

- `keepnames-github.sh` and `keepnames-gitlab.sh` are run to preserve `docinfo.xml` (and any other files/directories if configured), once per name. The way they work is by copying the files into the `drupal-build/$DISTRO` subdirectory in the GitHub directory, where the generated files reside. At the next step, the content of the GitLab branch is deleted entirely and the content of `drupal-build/$DISTRO` is copied over to the GitLab branch.

- `aura.tar.gz` is a Python library that is installed as a prerequisite. It is really needed only in the `image` subdirectory, but was left in the root too, in case someone needs to use the CI without a custom container (saved in the `full-ci` directory, see below) again.

- `image` contains the source for building the custom image used for the server run. This image is based on Red Hat UBI with the necessary dependencies (notably, libraries for running `build_for_portal.py`) installed. It has a user named `syncserver` and this user is set as default, so the CI runs as that user. But it also has a script to add certificates, which is run via sudo. The script is there because we need to add Red Hat certificated but the image might be in a public repository, so we add the certificates at CI run time.

### Additional files

Files for earlier attempts without a custom image and with a Debian-based custom image can be found in the `add-gitlab-ci-experimental` branch, That branch also contains a job for triggering quay.io image rebuilds via a github push; it was not put in production for now.
